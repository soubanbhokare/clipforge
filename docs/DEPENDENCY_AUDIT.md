# CLIPFORGE — Dependency & Supply-Chain Audit (Phase 13)

- **Date:** 2026-11-02
- **Scope:** root package (`~/workspace/CLIPFORGE`, React/Vite frontend) + `server/` package (Express backend), both `package-lock.json` files, the Python/system runtime the server spawns, and the ONNX models in `server/models/`.
- **Mode:** READ-ONLY. Nothing was installed, upgraded, removed, or edited in `package.json` / lockfiles / source. The only files created are this report and `~/workspace/CLIPFORGE/sbom.json`.
- **Environment at audit time:** Node v24.22.1, npm 10.9.4, Python 3.12.3, ffmpeg 8.1.2.

## 0. Method — and an important honesty note about `npm audit`

`npm audit` was run in **both** packages (plain and `--json`). **It failed in both places for an infrastructure reason, not a project reason:**

```
npm warn audit 403 Forbidden - POST https://registry.npmjs.org/-/npm/v1/security/audits/quick - policy_denied
x-hatch-policy: zz_managed_internal_spaces_package_registries
"POST /-/npm/v1/security/audits/quick not permitted by policy"
```

The managed network policy on this machine blocks the npm audit endpoint, so **npm returned zero advisory data — that is NOT the same as "zero vulnerabilities."** Registry reads do work (`npm outdated` succeeded), so this audit fell back to:

1. Full lockfile analysis (versions, licenses, duplicates, install scripts, integrity hashes) for all 445 lock entries.
2. Import-level usage analysis of `src/`, `server/src/`, `server/tests/`, `server/scripts/`.
3. Manual cross-check of the highest-risk installed versions against public advisory sources (GitHub Security Advisories / NVD / vendor security releases, retrieved 2026-11-02).

**Coverage limit:** the manual cross-check covered the direct production dependencies and the transitive packages with known recent advisory activity. It is not a substitute for a real `npm audit` run. **Recommendation R1: re-run `npm audit` for both packages from a network where the audit endpoint is allowed before any production launch, and treat its output as the authoritative advisory list.**

`npx @cyclonedx/cyclonedx-npm` was also attempted for SBOM generation and timed out on this network; the SBOM was instead generated by a lockfile-parsing script (see §7), which the task allowed.

## 4. Unused / undeclared / duplicate dependencies

### Declared-but-unused: **none**

Import scan of 88 root source files + `vite.config.ts`, and 37 server TS/JS files:

- Root: `react` (49 files), `react-dom` (`src/main.tsx`); devDeps `vite`, `@vitejs/plugin-react` (both in `vite.config.ts`), `typescript` + `@types/*` (build/`tsc`). All used.
- Server: **all 9 production deps are imported in `server/src/`** — `@node-rs/argon2`, `cookie-parser`, `express`, `express-rate-limit`, `multer`, `zod` (broadly), `exceljs` + `pdfkit` (`analyticsReports.ts`), `nodemailer` (`email.ts`). All devDeps are used (`tsx` by start/dev/test scripts, `typescript` by build, `@types/*` by `tsc`).

### Used-but-undeclared

- **npm: none.** Every non-builtin import in both codebases resolves to a declared dependency; everything else is `node:` builtins.
- **Python: the entire layer is undeclared.** `server/scripts/transcribe.py` imports `faster_whisper`, `numpy`; `server/scripts/track.py` imports `numpy`, `cv2` (opencv), `onnxruntime`, `faster_whisper` (VAD). **There is no `requirements.txt`, `pyproject.toml`, or Pipfile anywhere in the project** (verified by filesystem search). The versions in §7/the SBOM are whatever the machine image happens to have — the project's most serious reproducibility gap.
- **System tools are implicit dependencies:** `ffmpeg`/`ffprobe` (spawned across `media.ts`, `analysis.ts`, `editor.ts`, `export.ts`, `broll.ts`, `tracking.ts`), `fc-list` (`captions.ts`), and the ONNX models in `server/models/`. None are declared in any manifest; they exist only as runtime probes in `admin.ts` health checks.

### Misclassified dependency (production risk, not "unused")

- **`tsx` is a server devDependency but is the production runtime:** `"start": "tsx src/index.ts"`. A production install with `npm ci --omit=dev` (or any dev-pruning deploy) **breaks `npm start` entirely**, and production currently executes TypeScript source through tsx/esbuild instead of the compiled `server/dist/` output that already exists. Move `tsx` to dependencies *or* change `start` to run the built output — a coordinated lead decision; not changed here.

### Duplicates

- **Root lockfile: none** — 115 entries, 115 unique names.
- **Server lockfile: 330 entries, 301 unique names; 12 names at multiple versions:**

  `@types/node` (14.18.63 + 22.20.5), `@types/send` (0.17.6 + 1.2.1), `archiver-utils` (2.1.0 + 3.0.4), `base64-js` (0.0.8 + 1.5.1), `brace-expansion` (1.1.21 + 2.1.7), `isarray` (1.0.0 + 2.0.5), `minimatch` (3.1.5 + 5.1.9), `ms` (2.0.0 + 2.1.3), `pako` (0.2.9 + 1.0.11), `readable-stream` (2.3.8 + 3.6.2), `safe-buffer` (5.1.2 + 5.2.1), `string_decoder` (1.1.1 + 1.3.0) — plus same-version nested copies (`isarray@1.0.0` ×5, `readable-stream@2.3.8` ×5, `safe-buffer@5.1.2` ×5, `string_decoder@1.1.1` ×5).

  All are normal consequences of the legacy exceljs/archiver/unzipper tree coexisting with the modern Express tree — bloat and audit noise, not a correctness bug. Notable: `@types/node@14.18.63` sits in the **production** tree only because `@fast-csv/format`/`@fast-csv/parse` declare `@types/node@^14.0.1` as a runtime dependency — a types package shipped to production (inert at runtime).
- **Across the two packages:** `typescript@5.9.3` identical; `fsevents@2.3.3` identical; `esbuild` (0.21.5 vs 0.28.2) and `debug` (4.4.3 vs 2.6.9) diverge — expected for two independent trees, and the reason A1 affects only the frontend tree.

## 6. Pinning & reproducibility verdict

- **Version ranges: 100% caret ranges (`^`) for every direct dependency in both packages.** No exact pins, no `overrides`, no `.npmrc`, and **no `engines` field** in either `package.json` (Node 24 is assumed, never declared — the server also depends on `node:sqlite`, so the Node floor matters and is undocumented in the manifest).
- **Lockfiles: both present and complete** — `package-lock.json` (root, 58K, lockfileVersion 3, 115 entries) and `server/package-lock.json` (151K, lockfileVersion 3, 330 entries), with sha512 integrity hashes (all 425 SBOM npm components carry hashes). `npm ci` from these files reproduces both trees exactly. **Caveat:** this workspace copy has **no git repository**, so "committed" cannot be verified from here — whoever owns the real repo should confirm both lockfiles are tracked.
- **Install scripts: minimal and benign.** Only `esbuild` and `fsevents` have `hasInstallScript` in either lockfile, both dev-tree only (esbuild links its platform binary; fsevents is a macOS-only optional watcher). **No production dependency runs an install script.** `@node-rs/argon2` ships prebuilt binaries via platform optional-dependencies, no script execution.
- **Python/system layer: not reproducible at all** (no manifest, §4). The npm side would survive a rebuild; the STT/CV side would silently become "whatever the next machine image has."

**Verdict: npm reproducibility = GOOD (lockfile-driven, conditional on using `npm ci` and tracking both lockfiles in VCS). Whole-system reproducibility = PARTIAL, failed by the undeclared Python/system layer and the undeclared Node engine floor.**

## 8. Recommendations (for the lead — none applied by this audit)

- **R1.** Re-run `npm audit` (both packages) from an unrestricted network before launch; this report's advisory section is a manual partial check (§0/§1c).
- **R2.** Plan the Vite 5 → supported-major upgrade (fixes A1+A2 together); until then, don't expose `npm run dev` beyond localhost-trusted networks (`server.host: true` in `vite.config.ts`).
- **R3.** Fix the `tsx`-as-production-runtime classification (§4): move `tsx` to dependencies or start from `server/dist/`.
- **R4.** Add a pinned Python manifest (`requirements.txt` with the §7 versions) and declare `engines.node` in both `package.json` files.
- **R5.** Plan an `exceljs` replacement for XLSX export; it is unmaintained, holds the only unknown-license package (`buffers`), and most of the duplicate-version bloat.
- **R6.** Record the jszip MIT license election (§3) wherever license compliance is tracked; confirm both lockfiles are tracked in the real VCS.
